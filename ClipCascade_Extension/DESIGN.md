# ClipCascade Chrome Extension: Design

## Goals

- A Chrome (Manifest V3) client for ClipCascade **server mode** (`CC_P2P_ENABLED=false`).
- **No server changes.** The extension speaks the exact protocol the desktop and mobile clients use.
- **Hybrid capture:**
  - *Browser copies* (default on): copy/cut events in web pages trigger a clipboard read.
  - *System clipboard polling* (opt-in): also picks up copies made in other apps, like the desktop client does.
- Interoperable end-to-end encryption with the other clients.

Non-goals for v1: P2P mode, Firefox (it has no `chrome.offscreen`).

## Protocol (from the existing clients)

| Step | Request | Notes |
|---|---|---|
| CSRF | `GET /login` | Token is in the hidden `<input name="_csrf">` of the login form. |
| Login | `POST /login` (form) | `username`, `password = sha3_512_hex(raw password)`, `_csrf`. Success redirects to `/`, failure to `/login?error`. Session is the `JSESSIONID` cookie. |
| Check | `GET /validate-session` | Body `OK` when the cookie is valid. |
| Mode | `GET /server-mode` | `{"mode": "P2S" \| "P2P"}`. P2P is rejected with a clear message. |
| Limit | `GET /max-size` | `{"maxsize": bytes}`. Checked against the raw clip before sending. |
| Socket | `ws(s)://<server>/clipsocket` | STOMP 1.2. Subscribe `/user/queue/cliptext`, send `/app/cliptext`. |

Message body: `{"payload": string, "type": "text" | "image" | "files"}`

- `text`: the text itself
- `image`: base64 PNG (or any format the receiver can decode)
- `files`: JSON string `{"<file name>": "<base64 content>", ...}`

### Encryption (must match `ClipCascade_Desktop/src/utils/cipher_manager.py`)

- Key: `PBKDF2-HMAC-SHA256(password, salt = username + password + saltSetting, rounds = 664937, dkLen = 32)`.
- Cipher: AES-256-GCM with a **16-byte nonce** and a 16-byte tag.
- The payload becomes the JSON string `{"nonce": b64, "ciphertext": b64, "tag": b64}`.
- Web Crypto returns `ciphertext || tag`, so the tag is split off and re-appended.
- `tests/fixtures/` holds vectors generated by Python, so the JS side is checked against the reference implementation.

## Architecture

```
 content script (all pages)             popup / options pages
   copy/cut event ──┐                     sign-in, status, send box, history
                    ▼                           │  runtime messages
        ┌─────────────────────── service worker (coordinator) ───────────────────────┐
        │ auth (fetch + cookie jar)   crypto (Web Crypto)   history (storage.session) │
        │ websocket cookie rule (DNR) context menus, shortcut, notifications, alarm   │
        └───────────────┬────────────────────────────────────────────────────────────┘
                        │ runtime messages: connect / publish ⇅ socketStatus / socketMessage
                        │                   read / writeText   ⇅ clipboardChanged
        ┌────── offscreen document (reason CLIPBOARD, no lifetime limit) ──────┐
        │ STOMP client (@stomp/stompjs) → wss://<server>/clipsocket            │
        │ clipboard: execCommand('paste') → paste event; execCommand('copy')   │
        │ polling loop + dedupe hash                                           │
        └──────────────────────────────────────────────────────────────────────┘
```

Why each piece lives where it does:

- **The offscreen document holds the socket.** Chrome applies `declarativeNetRequest` rules to websockets opened by extension pages but not to ones opened by the service worker, and the rule is needed to send the session cookie (see below). The offscreen document has no lifetime limit, so the connection doesn't depend on the worker staying awake either. It only relays frames: encryption, sessions and history stay in the worker.
- **The service worker coordinates.** It wakes for runtime messages, and a 30 s `chrome.alarms` alarm recreates the offscreen document and socket if Chrome ever closes them. Its state lives in `chrome.storage.session`, so it survives the worker being evicted.
- **The offscreen document owns the clipboard.** Service workers have no clipboard access. Polling runs there too, so the worker is woken only when the clipboard actually changes.
- **Reading uses the paste event, not `navigator.clipboard`.** The async API requires focus, which the offscreen document never has. `execCommand('paste')` (needs `clipboardRead`) fires a `paste` event whose `clipboardData` exposes text *and* image/file items without focus.
- **Images and files are written from the popup.** Writing an image to the clipboard needs a focused document, so received images and files land in the popup history (and a notification). The popup copies them with `navigator.clipboard.write`, and files download with `chrome.downloads`. Received text is written automatically.
- **Loop prevention:**
  - The offscreen document keeps a hash of the last clipboard content it saw or wrote. Content the extension writes is recorded before writing, so it is never echoed back.
  - For images the popup writes, the next change within 3 s is adopted as the baseline, because Chrome may re-encode the PNG.
  - The server echoes every message to all of the user's sessions, including the sender, so the worker drops incoming clips matching its last few sends.

## Sessions and secrets

- Cookies live in the browser's cookie jar for the server origin. Signing in to the web dashboard in the same browser therefore shares the jar; the server allows unlimited sessions, so this is harmless for the same account.
- **The websocket handshake needs help.** Verified against a real server:
  - Chrome sends the `SameSite=Lax` `JSESSIONID` cookie with the extension's `fetch` calls, but **not** with a websocket handshake from the extension.
  - Without the cookie, the server redirects the handshake to `/login`.
  - `;jsessionid=` in the URL is rejected by Spring Security's firewall (HTTP 400).
  - The fix: before every (re)connect, the worker reads the server's cookies with `chrome.cookies` (which can read HttpOnly cookies). It installs a session-scoped `declarativeNetRequest` rule that sets the `Cookie` header.
  - The rule matches only `ws(s)://<server>/clipsocket` requests that don't come from a tab.
- The raw password is never stored. At login it is turned into the SHA3 hash (server login) and the PBKDF2 key (encryption).
- Default: both live in `chrome.storage.session` (memory only, cleared when the browser exits).
- "Remember me": both are also kept in `chrome.storage.local`, matching the desktop client's `save_password`. The worker then re-authenticates silently after a browser restart or session expiry.
- Signing out happens only when the server rejects the credentials. When the server is offline or errors, the worker keeps retrying.

## Permissions

| Permission | Why |
|---|---|
| `<all_urls>` host access | Talk to a user-chosen server; run the copy listener on every page. |
| `clipboardRead`, `clipboardWrite` | Read and write the clipboard from the offscreen document. |
| `offscreen` | The clipboard document. |
| `storage`, `alarms` | Settings, session state, keepalive. |
| `cookies`, `declarativeNetRequestWithHostAccess` | Attach the session cookie to the websocket handshake (see above). |
| `contextMenus`, `notifications`, `downloads` | Right-click send, receive alerts, saving received files. |

## Known limits

- Polling reads only what Chrome exposes in a paste event: text everywhere, images when copied as images. Files copied in a file manager show up on some platforms only.
- TLS is Chrome's: a server with a self-signed certificate must be trusted by the OS or browser first.
- Self-hosters who set `CC_ALLOWED_ORIGINS` must add `chrome-extension://<extension id>` for the websocket handshake.
- **Server race (not specific to the extension):** two clients of the same account signing in from the same IP at the same moment can make one of them fail with HTTP 500.
  - Cause: `FacadeUserService.setLoginDetails` gets `null` from `BruteForceProtectionService.removeIpDetails` when the other login already removed the entry.
  - The extension treats a 500 as transient and retries on the next reconnect.
