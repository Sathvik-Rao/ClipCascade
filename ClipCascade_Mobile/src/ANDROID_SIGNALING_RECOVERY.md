# Android ClipCascade signaling recovery (10 October 2026)

## Repro and root causes

The Samsung Galaxy S25 app showed `✅ Connected` / `📊 Peers: 0` while Nox had only the Glass websocket peer. Tapping Stop then Start recovered `Peers: 1`, but a transient handshake returned `Expected HTTP 101 response but was '200 OK'` before reauthentication succeeded. The old APK was also a **debug build** repeatedly trying to attach to `localhost:8081` Metro, which was not running.

The Android WebSocket code previously only retried when `wsSignalingClient` became `null`. A half-open socket that never delivered `onclose` could retain a stale `✅ Connected` status forever. The backend already sends WebSocket protocol ping frames, but the JS app cannot observe the native pong lifecycle. It now sends a JSON `{ "type": "PING" }` every 25 seconds; the server sends `{ "type": "PONG" }`. After a sent PING remains unanswered for 75 seconds, Android invalidates and closes the stale socket, clears old P2P peers, and uses its existing authenticated retry (10 seconds). A paused/backgrounded Android JavaScript loop gets a fresh probe on resume instead of immediately triggering a false timeout. `socket.onerror` also invalidates the reference instead of relying solely on a missing `onclose` callback.

## Subsequent 10 October reliability hardening

- A content-free `_cc_probe` PING/PONG is now exchanged over the actual WebRTC **data channel** in both directions. This detects a stale channel that still claims to be open and proves transport delivery without changing the user's clipboard. The Glass daemon records only proof freshness, and the Nox monitor treats missing proofs as a failure.
- Android's foreground service verifies unacknowledged data channel probes, and it tolerates long JavaScript event-loop suspension while the phone sleeps. The new `DataChannelProbes.test.js` covers bidirectional messages, ignored forgeries, failure timeouts and suspension.
- `BootReceiver` handles `MY_PACKAGE_REPLACED`: installing a correctly signed release does not leave sync dead until the user manually opens the app. Verified with an actual data-preserving upgrade while Samsung was locked and a fresh matching P2P proof.
- Shizuku clipboard UserService is checked by the existing native 5-second watchdog. An unhealthy binder or failed callback registration is unbound and re-established. Verified by terminating only the shell-owned `com.clipcascade:clipboard` subprocess: a new process appeared in about 15 seconds, and Android logged `Shizuku clipboard callback recovered`.
- The Nox `clipcascade-health-guard.timer` verifies Android foreground/recovery processes, the separate Shizuku listener, the non-debug release build, HTTPS signaling, and recent payload round trips every two minutes. Sustained failure sends Matrix alerts and can restart the Glass daemon with a cooldown.
- Use `scripts/install_samsung_release.py` for safe builds and in-place upgrades. It verifies the original APK signing identity and rejects debug APKs; it never uninstalls or clears Android app data.

**Acceptance tests passed:** Android locked-device in-place upgrade and automatic recovery, successful Glass → Samsung → Glass P2P challenge/response, recovery of P2P challenge/response after controlled Nox server and Glass headless restarts, native Shizuku clipboard subprocess crash/rebind, 10 Jest cases, signed release Gradle build, Nox guard tests and live scheduled guard run. Testing actual clipboard *contents* through the UI still requires a reversible fixture test while the device is unlocked. Do not equate a verified data-channel probe with proof that every clipboard MIME type works.
